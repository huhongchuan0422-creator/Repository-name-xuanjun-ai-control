# 社区分账系统：微信渠道、开源复用与服务器落地前置

日期：2026-10-14。来源：Owner补充及 Stage5 原需求。状态：DOCUMENTED_ONLY / HOST_VERIFICATION_NOT_RUN / PRODUCTION_DEPLOYMENT_NO。

## 必须交付的五个界面与后端
1. 商家展示前端（商家主页、门店、商品/服务、活动、地址、客服、支付入口）。
2. 微信小程序消费者端（商家展示、扫码/场景关联、金额输入、支付中与服务端已核验的收据页）。
3. 公众号H5消费者端（对应的微信内网页，按公众号OAuth/JSAPI实际权限接入）。
4. 商家管理后台（自有门店、员工、订单、退款、结算/分账查询、广告与展示素材）。
5. 平台管理员后台（入驻审批、跨商家运营但受限授权、支付通道与分账规则、审核、风控、财务对账、系统审计）。

**共同后端**：租户RBAC、店铺、支付订单、支付服务商适配、回调/查询对账、退款、分账指令/结算、广告引擎、操作审计。广告独立失败降级不影响支付。

## Owner 2026-10-14 英国多容器部署最终决策（覆盖以上旧建议）

**已确定部署归属**：社区分账系统与公益视频平台都部署在既有**英国服务器**，依托其多容器能力实施项目级隔离。无需因原方案要求“独立Stage5物理服务器”而另外采购主机；以上服务器表的旧英国“不可运行支付”及另购独立物理机建议被本节替代。除既有英国P2/P3控制面及这两个指定业务以外，其他新项目原则上不再部署英国服务器。东京、韩国、国内已有项目不因此迁移或删除。

### 规划的隔离布局（目标，不代表已部署）
- 英国开发控制面（现有P2/P3）：独立容器/运行用户、网络、日志和身份；不得给社区分账或公益视频容器访问control ledger、Runner执行权限、Docker socket及开发OAuth。
- `uk-community-payment`：独立应用容器、数据库容器或独立DB实例、对象资源桶/路径、受限网络、专属密钥SecretRef、审计和独立备份。商家展示、小程序/公众号API、商户后台、平台后台、支付回调、分账/退款/对账、两个广告位属于同一业务域；生产收款和正式分账必须额外通过支付/隐私/Release门禁。
- `uk-public-benefit-video`：独立API/转码worker/队列/数据库/对象存储、网络和SecretRef；不能共用社区支付数据库、凭据、上传目录或工作队列。视频转码/AI任务先设计内存/CPU/磁盘/网络配额及有界并发，不得挤占收款回调和英国控制面。视频原件及产物建议以独立对象存储和生命周期策略管理，采购以实际容量测算为准。
- 共用资产仅限经过容量核验的英国主机、受控反向代理/证书基础设施及机械监控；各项目须独立域名路由、容器网络/卷、数据库角色、最小权限及备份恢复。支付与视频可共用物理节点但不得互通内部服务或秘密。

### 容器上线的先验安全门禁
1. 英国主机只读核验：CPU/内存、磁盘、Docker/Podman版本、容器/网络/端口/卷、cgroup、现有P2/P3服务、Nginx主配置与443/80路由、当前资源余量。不能仅凭“支持多容器”断言容量足够。
2. 固定容器资源上限（CPU、内存、PID、磁盘/日志），并设置健康检查、异常重启限制、启动依赖、升级回滚与故障告警；拒绝特权容器、宿主机敏感路径挂载、host network和共享Docker socket。
3. 为支付与公益视频分别建立业务代码仓库、CI/CD、数据库备份及恢复演练、可审计发布制品、密钥引用。非公开环境或秘密不写入GitHub。
4. 确认微信支付/公众号/小程序的主体、域名、回调IP、支付分账授权、数据合规与视频内容审核/存储地域规则；未确认则可以离线开发/模拟联测，不能上线真钱或客户内容。
5. 不得以新增容器干预当前P2 HOLD/恢复事务、现有Fence/Writer/Runner或者旧隔离服务。每个业务分别进行安全审核和生产Release。
