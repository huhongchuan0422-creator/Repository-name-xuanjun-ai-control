## 1. 结论与一次授权边界

建议采用“项目完整能力集 + 每次调用的机器准入”，而不是逐个功能申请sudo。一次冻结英国、国内、韩国的全部开发与日常运维动作、目标服务/目录/数据范围、既有身份、回滚和撤销策略；精确包独审并激活后，同范围内日常动作由固定策略校验，不再因遗漏某个普通运维命令反复申请。东京只保留迁移所需权限，迁移验收后退役。

机器准入始终核身份、任务/spec、目标仓库与主机、路径/服务、制品、lease/fence/epoch、独立审核、允许动作、有效授权及结果对账。项目能力齐全不等于任意root shell，也不代表现有生产切换、交易/资金、身份签批和凭据门禁已经通过。

长期权限激活本身会创建或扩大持久访问，因此必须在实际配置、身份、目标、权限差异、精确hash和撤销方案就绪后，另取得一次针对完整包的明确动作时确认。当前用户意图足以继续准备和设计，不能用泛化“最高授权”替代该精确激活确认。一次包可以覆盖所有已列日常能力；以后同范围普通动作不重复申请能力。新主机/数据域/凭据/安全边界或实质风险扩大需新确认；即使仍在原范围，政策明确要求动作时确认或人工完成的具体事项，例如不可恢复删除、安全设置变更、金融交易及原生产恢复签批，仍逐项保留。这不是把普通运维重新拆成零散授权。

## 4. 身份与信任分层

| 身份层 | 可持有能力 | 必须隔离的能力 |
|---|---|---|
| ChatGPT / Work / DOTS真实入口 | 各自原生生成代码，向获准任务提交；读取脱敏回执 | 入口字符串、同GitHub账号评论不能自证平台身份；不得伪造其他平台或自审 |
| 项目开发/测试进程 | 独立任务工作区、分支、依赖缓存、测试输出 | 无主机root、生产凭据、生产数据库、容器管理socket；无任意sudo |
| 可信项目调度者 | 核task/spec/path、claim/renew/fence、发布固定请求 | 不能自行改授权策略、签独审、扩大目标或给Runner root |
| root-owned broker/已审发布入口 | 固定操作ID映射到固定实现，核目标和授权，执行业务所需系统动作 | 拒绝任意shell、脚本路径、unit、UID、环境注入、未审制品和不受限参数 |
| 运行服务身份 | 最小运行目录、必要的既有凭据句柄/文件读取、特定数据域 | 不向开发Runner导出凭据；不兼任信任根或发布审核者 |
| 独立审核者 | 读取精确源码/制品/脱敏证据，签自己未开发范围 | 无被审源码写入及自我批准；审核版本变化仅影响相关范围 |
| Owner / 管理员救援入口 | 明确的控制台救援、精确持久授权与安全设置变更 | 不共享给PR代码；保留可验证的撤销与故障恢复入口 |

同一Unix UID可以承载现有工具，但不能提供独立平台身份或审核独立性。审核分离必须有可信会话/平台来源、实际参与者登记和签批绑定；不能只改用户名。不存在合适隔离时保持该能力未启用，其他已验能力继续。

路径/lease检查本身不能约束已经运行的恶意进程。每个不可信任务必须有内核实际强制的文件系统与进程边界：只能写自己的任务挂载，不能访问其他任务工作区、Git元数据、可信调度者socket/config、共享凭据或审核目录；不能ptrace/发信号/读取其他任务进程敏感状态，不能借已打开FD、宿主挂载、用户命名空间或容器管理socket逃逸。同UID任务只有在这些边界实际成立并负测后才允许并行；否则保持不可启用并在统一包明确必要隔离变更。独立目录名称、不同分支和cgroup资源限制不等于安全隔离。HOME、临时目录、可写缓存按任务隔离；可共享缓存只读且hash绑定，不能跨任务投毒。复用现有账号不意味着接受共享信任域。

## 6. broker与发布入口的实施设计

不改动正在送审的P2源码。先在本设计中定义能力目录和逐机配置，待原canonical归属安排实施。若现有broker不能承载某类运维动作，应在同一项目控制面做独审的固定动作适配层；不创建第二调度器、不重写P2、不把现有Codex broker强行扩成任意命令代理。

- 请求仅含能力ID、固定host/service/data-scope ID、task/spec/attempt、输入制品摘要及受信任授权引用。路径、UID、systemctl参数、工具绝对位置和环境由root-owned策略决定；调用方不得传任意argv/script/env。
- 权限决策与执行之间重核版本/epoch/lease/fence/撤销状态，失败关闭；收到过期请求、未知结果或不匹配对象保持HOLD。
- root代码、配置、解释器、依赖、所有祖先和unit/drop-in须不可被Runner/开发者/服务用户写入；检查ACL/capability、硬链接、symlink、挂载与实际namespace，不只看文件owner。
- 英国历史上有root能力，因此移除sudo只能约束未来，不能证明现有root-owned链条此前未被改写。本设计没有发现或断言入侵，但激活前必须把安全关键解释器/二进制/依赖、服务/drop-in、broker/授权策略、信任存储和所有被root执行输入与独立认可的准确制品/可信系统基线比较，核安装来源及差异。owner=root不等于来源可信；无法建立可信基线时HOLD，集中提出经批准的干净恢复路径，保留admin救援与证据，不能一删sudo即宣称已安全。
- root执行不能直接import/run开发者PR脚本。代码按不可信数据处理，完整制品经过冻结、独审与promotion后才进入root保护目录。安装器本身从可信版本加载，不来自待安装包自带脚本。
- 仅给某用户“固定sudo命令”还不够：若命令有任意参数/配置、可执行用户脚本、PATH/动态加载注入、可写unit、Docker socket、可写root cron或任意文件安装，仍可等价root，必须否决。
- 保留admin控制台救援；Runner不给无条件NOPASSWD:ALL。英国历史宽权先由只读取证列出实际生效来源，再用精确包移除/收紧对应规则，不能只添加窄规则而留下宽规则。
- 每个动作有最大运行时长、资源配额、明确副作用类型、幂等键和读回规则。每项实质副作用之前先持久化已经授权的intent、目标、精确输入和幂等身份并fsync；完成后持久化outcome，无法确定则记录UNKNOWN。外部审计目的地中断时可使用有容量上限的root保护本地spool，恢复后按序去重补传；本地无法持久化、spool满或fsync失败必须阻止新的变更，不能先做效果再补日志。网络断线后先查询journal和目标状态；不凭客户端超时盲重做。
- 审核者只能签其未开发范围；审核凭证绑定actor/platform/session、scope、HEAD/tree/artifact、有效期与决策。相同GitHub账号可运输记录，但不是独立身份的证明。

## 8. 安装、验证、撤销和回滚交付要求

当前只交付步骤规范，不提供臆造sudo/root命令。现有sudo实际规则、长期操作adapter、unit/path及最终bundle未确定，任何能粘贴执行的安装命令都会是假精确。

完整包应包含：逐机manifest、能力策略、账号/服务/目录映射、原状态快照摘要、全部源码/依赖/制品hash、精确变更diff、独立审核回执、只读验证入口、一次安装入口、验证入口、撤销入口、失败回滚入口、恢复点、预期终态和已知不可逆效果。每个入口使用固定绝对路径和固定操作，不支持传任意文件/命令。

安装顺序：
1. 收集第7节缺失证据，冻结完整能力范围。固定已完成的盘点和未变已审制品；不碰UK停机状态。
2. 在隔离测试环境实现/验证统一包，测试全部正反例；独审整个影响链，一次汇总修复。P2当前受审源保持原样。
3. 独审后的包生成准确hash、逐机diff及执行/撤销命令；一次列清所有主机、既有身份、长期权限和残余门禁，取得完整包激活动作时确认。GitHub管理部分待真实管理员入口就绪。
4. 在每台目标机执行只读verify-only：校验主机/epoch/原状态/入口/权限/backup、writer互斥、依赖、磁盘和管理员救援可用性。不得顺带修权限、创建目录或启动服务。
5. 管理员控制下开启单事务维护锁，保存精确前态，使用root保护新目录stage。每一步先写durable intent和幂等身份再做批准diff，随后写durable outcome/UNKNOWN并读回；本地审计持久化失败停止新增效果。四机不是一个分布式原子事务：逐机记录成功/失败，其他机器不得假报成功；有跨机依赖则阻断受影响启用。
6. 先证明受控新路径与救援/撤销可用，再精确移除旧宽权；不得让未审Runner在新旧权限并存窗口执行。不能为了完成此步擅自停止活跃生产unit，需纳入精确维护方案。新入口默认禁用，完成负向隔离与审计后仅启用被批准能力。
7. 只做批准的最小可逆演练：临时项目工作区/非生产样例服务/测试数据，验证全矩阵权限边界与撤销。撤销演练结束时状态必须为REVOKED/DISABLED，不能同时声称ACTIVE。UK必须等其P2阶段准入，不能借演练启动旧/新writer或Runner。Tokyo只做迁移必要演练。
8. 若要最终启用，必须有适用于这一次精确重新激活的有效动作时确认，重新核原状态、身份、hash、epoch和全部门禁，再进行受控激活及最终有效权限读回。一次精确安装确认可以事先明确包含本次有界事务内“撤销演练→拒绝验证→同版本重新激活→读回”的固定步骤，避免临时拆开申请；事务已结束、版本/范围改变或重新激活未被精确覆盖时必须新确认。不能用演练前的状态或旧批准猜测恢复授权。仅实际当前生效且验收通过才留下ACTIVATION_RECEIPT并标ACTIVE。否则保持REVOKED/DISABLED/HOLD。失败保留journal；未验能力不可标ACTIVE。当前项目生产健康与具体业务验收另外记录。

撤销：禁新claim/请求→递增并持久化fence/revocation版本→按固定映射停止在途并核cgroup空→对账未知外部效果→撤销所安装策略/能力映射/必要平台授予→读回所有身份无残留能力。保留审计与备份，admin救援不删除。修改用户名或删一个sudo文件不是完整撤权，必须覆盖组/ACL/socket/服务/旧授权和平台token路径；不接触/输出token值。

回滚：只恢复本事务变更的准确bytes/owner/mode/ACL/unit/config与已批准安全状态，绝不默认恢复NOPASSWD:ALL。若旧宽权曾是前态且安全回退没有获批，采取fence-stop保留现场与admin救援，不自动恢复不安全授权。数据、对外通知和交易的副作用未必可逆；未知状态HOLD，不宣称全部undo。P2仍遵守FENCE_STOP_RETAIN_NO_REPLAY。
