# 开发执行与反馈强制规则

生效日期：2026年10月12日。授权来源：Owner 胡洪川本次指令。
适用范围：玄钧云汇、英国 P2/P3，以及 Work、GitHub、Runner、OpenClaw 的后续开发协作。本规则补充 V2.7 开发运作规范；不变更既有架构、模型、预算和生产权限。

## Owner 要求

1. 我不听汇报，我只要结果。
2. 我不要等待，我要每项节点都正常推进，每个任务在执行。
3. 事事有回应，任务有反馈。不要后面的事情中断了，也不知晓。

执行解释：以代码、可审核制品、真实执行回执和验收结果交付；汇报不能替代行动。依赖已满足且在授权范围内的任务必须主动推进，不等 Owner 再喊下一步。受阻节点必须进入明确的阻塞状态，不能假装执行；独立可执行节点继续。真实依赖、安全门禁与额度限制不能靠伪造运行绕过。

## 每个节点必须有人负责且有执行证据

Work 对任务推进与反馈闭环负责，Runner/OpenClaw 对实际执行及回执负责。沿用现有任务账本、父任务、唯一执行者、租约、fence 和预算；不另建平行队列。
每个节点必须记录：任务及尝试 ID、依赖、负责人、执行入口、源提交及制品摘要、当前状态、开始时间、最后真实进度时间、run/session/unit 或可用 PID、checkpoint、下一动作及期限。
区分 SUBMITTED、RECEIVED、STARTED、PROGRESS、COMPLETE、FAIL、HOLD。提交评论、读取源码、CI 排队或监督心跳均不代表开发者已启动；心跳不能替代子任务真实进度。
READY 节点须在可用容量内立即调度；容量不足则明确 QUEUED，不能称为 RUNNING。BLOCKED 节点须说明具体依赖、解除责任人和下一检查时点。

## 缺回执的处理时限

时限从真实提交事件开始，基于持久时间戳；重复评论不重置时钟。采样与平台启动延迟应单独记录。

| 触发条件 | 强制处理 |
| --- | --- |
| 提交后2分钟无 RECEIVED | 自动记录接收超时，Work 核查触发工作流、Runner 在线状态、实际收件入口；不能静默等待 |
| 提交后5分钟无 STARTED | 核查执行 admission、进程、lease/fence、权限和预算，返回实际启动证据或具体 HOLD 原因 |
| 已启动后10分钟无真实进度 | 核查子进程、错误、checkpoint 与外部副作用；监督心跳不得刷新进度时间 |
| 提交后60分钟无 COMPLETE/FAIL/HOLD | 记录终态超时并进入人工可见的阻塞处理；不得无限等待、重复重派或重置预算 |
| 同一根因30分钟未解决 | 给 Owner 一次明确异常反馈，同时评估更有效实现方式 |
| 同一根因60分钟未解决 | 暂停原失败方法，写入根因、失败证据、断点与替代方案，以 HOLD_METHOD_CHANGE_REQUIRED 管理 |

所有超时检测、哈希核对和日志整理优先使用确定性脚本，不用模型轮询。不确定旧执行者是否结束时，先核实并完成受控 stop/wait/fence，再决定恢复；禁止并发重复 writer。超时不是授权杀死未知进程或执行生产变更。

## 告警之后必须追踪并处理

告警只是异常记录。每条异常必须绑定处理责任人、下一动作、处理期限和最后处理证据；不能发完告警就结束。
Work 在活跃执行回合内必须读取回执、定位入口或依赖失败，并完成已授权的修复和验证。需要服务器命令时，先制作可审核且符合现有门禁的合并执行步骤，提供准确命令与预期结果；不能把自身未提供命令说成 Owner 未授权。
若后台无法唤醒 Work，必须明确标记该入口 NOT_VERIFIED 或 UNAVAILABLE，并建立可验证的替代处理路径。禁止承诺“我一直监控”“等待就会完成”，除非真实后台机制已部署且有测试证据。
通知失败必须记录并重试有界的幂等投递；不能仅在聊天里声称 Owner 已收到。GitHub 有告警不等于这个聊天已被唤醒，更不等于 OpenClaw 已恢复开发。

## 不丢后续任务

任务状态、依赖、最后进度、错误、断点、回执及下一动作必须持久化。上下文切换、聊天结束、进程退出、重启和额度耗尽不能抹掉队列。
前置任务完成后，要验证制品和验收条件，再推进已授权的后继 READY 节点；不能停下来等 Owner 逐项催促。失败或 HOLD 要把受影响的下游依赖标为 BLOCKED，并继续不受影响的任务。
恢复前核对 canonical ledger、实际进程、唯一 epoch/fence、已发生副作用和 checkpoint；未查清的执行结果保持 UNKNOWN，不重复执行。断电恢复与备份恢复须经实测后才标记 PASS。
聊天结束不能充当持久执行者；没有后台执行证据时须明确任务已停止或待启动。

## 交付与验收

每项交付须绑定实际代码/制品、commit/tree/hash、测试与必要独立审查、安装回执及回滚证据。源码完成、CI PASS、已安装、实机验收通过必须分开。
不能以不断增加计划、监控草案或审查描述替代当前关键路径交付。P2 优先交付完整、可审核的一体安装与回滚包，然后实际安装验收；P3 用真实任务验证。
节点完成必须产生可读取终态；未完成须产生具体 blocker、保留断点和可执行下一动作。没有证据不能称 PASS；写入本规则不代表相关运行能力已实现。

## 2026年10月12日14:51 文档与手机看板同步规则（Owner明确授权）

开发文档与现有私有系统中心看板必须同步；共用task/spec/checkpoint/attempt标识，不建立另一执行队列。文档记录架构、阶段、依赖、负责人及验收条件，看板在每个阶段下进一步拆解所有实际开发、测试、打包、审查、部署和恢复步骤；即使文档未逐项写开发过程，看板也必须记录这些细节。细分步骤只增加可观测性，不扩大开发权限。

每个事件和任务显示：负责人及实际执行入口、提交/接收/开始/最后真实进度/结束时间、排队时长、运行时长、无真实响应时长、实际run/session/unit、当前状态、checkpoint、下一动作、结果/错误和证据链接。无法证明的时间/执行者标UNKNOWN，不填0、不把责任人当实际执行进程、不把SUBMITTED当RUNNING。

5/15/30分钟取代此前2/10/15唤醒要求：5分钟未接收恢复收件；15分钟未启动或无真实进度核查并受控恢复原执行者；30分钟仍未恢复在看板记录阻塞与替代动作，确认旧writer停/fence失效后才接力。记录每次阈值触发、提醒投递、唤醒接收、重新STARTED、恢复结果及终态，分别验证，不能以提醒成功冒充重新执行。健康长任务不因耗时重复启动，监督心跳不刷新真实进展。默认反馈位置是看板，不要求Owner聊天催促或手动找OpenClaw；只有真实登录/人工安装等必要人工依赖列入人工待办。

每次状态转换先持久化权威执行证据，再更新看板；阶段或验收条件变化同步文档。展示证据更新时间、发布更新时间及同步延迟，更新失败保持旧快照并明确过期/失败，不伪造实时。英国自动数据回传未验收前显示快照，不能称该机制已部署。手机版为现有网址的响应式网页：任务卡片单列、无需横向拖动，时间统一Asia/Shanghai。

## 2026年10月18日 Owner长期规范：安装器默认最多5次受控尝试

适用玄钧云汇所有项目的新安装器、新版本安装方案及新执行许可。默认在同一准确批准范围内提供最多5次受控尝试，不能把“最多5次”实现为无条件循环、失败重放或必须执行5次。成功立即结束。

开发窗口负责实际代码实现、测试、提交、CI及证据闭环；Work负责独立核验实现是否真正支持以下机制。书面规则、许可文字或参数值改变，不证明能力已实现。

1. 每次执行具有独立Attempt编号、持久次数记录和完整日志；同一授权范围跨进程重启仍能对账，不能清零或复用Attempt。
2. 失败后先定位原因。只有可证明未写入，或已到达经核验的安全恢复点，并符合本次许可可重试条件时，才允许下一次Attempt。按检查点和输出指纹跳过已成功步骤。
3. 部分写入、结果UNKNOWN、并行Writer/租约/fence冲突，或无法证明安全恢复点时立即HOLD。先查询原执行及对账，禁止盲目重跑、并发派发或重置次数。
4. 保留备份、检查点、幂等及独占保护；禁止覆盖历史文件或删除失败证据来制造“首次执行”。成功或额度耗尽即终止该授权的继续执行。
