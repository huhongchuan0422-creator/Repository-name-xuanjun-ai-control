# 开发执行与反馈强制规则

生效日期：2026年10月12日。授权来源：Owner 胡洪川本次指令。
适用范围：玄钧云汇、英国 P2/P3，以及 Work、GitHub、Runner、OpenClaw 的后续开发协作。本规则补充 V2.7 开发运作规范；不变更既有架构、模型、预算和生产权限。

## Owner 要求

1. 我不听汇报，我只要结果。
2. 我不要等待，我要每项节点都正常推进，每个任务在执行。
3. 事事有回应，任务有反馈。不要后面的事情中断了，也不知晓。

执行解释：以代码、可审核制品、真实执行回执和验收结果交付；汇报不能替代行动。依赖已满足且在授权范围内的任务必须主动推进，不等 Owner 再喊下一步。受阻节点必须进入明确的阻塞状态，不能假装执行；独立可执行节点继续。真实依赖、安全门禁与额度限制不能靠伪造运行绕过。

## 每个节点必须有人负责且有执行证据

Work 对任务推进与反馈闭环负责，Runner/OpenClaw 对实际执行及回执负责。沿用现有任务账本、父任务、唯一执行者、租约、fence 和预算；不另建平行队列。
每个节点必须记录：任务及尝试 ID、依赖、负责人、执行入口、源提交及制品摘要、当前状态、开始时间、最后真实进度时间、run/session/unit 或可用 PID、checkpoint、下一动作及期限。
区分 SUBMITTED、RECEIVED、STARTED、PROGRESS、COMPLETE、FAIL、HOLD。提交评论、读取源码、CI 排队或监督心跳均不代表开发者已启动；心跳不能替代子任务真实进度。
READY 节点须在可用容量内立即调度；容量不足则明确 QUEUED，不能称为 RUNNING。BLOCKED 节点须说明具体依赖、解除责任人和下一检查时点。

## 缺回执的处理时限

时限从真实提交事件开始，基于持久时间戳；重复评论不重置时钟。采样与平台启动延迟应单独记录。

| 触发条件 | 强制处理 |
| --- | --- |
| 提交后2分钟无 RECEIVED | 自动记录接收超时，Work 核查触发工作流、Runner 在线状态、实际收件入口；不能静默等待 |
| 提交后5分钟无 STARTED | 核查执行 admission、进程、lease/fence、权限和预算，返回实际启动证据或具体 HOLD 原因 |
| 已启动后10分钟无真实进度 | 核查子进程、错误、checkpoint 与外部副作用；监督心跳不得刷新进度时间 |
| 提交后60分钟无 COMPLETE/FAIL/HOLD | 记录终态超时并进入人工可见的阻塞处理；不得无限等待、重复重派或重置预算 |
| 同一根因30分钟未解决 | 给 Owner 一次明确异常反馈，同时评估更有效实现方式 |
| 同一根因60分钟未解决 | 暂停原失败方法，写入根因、失败证据、断点与替代方案，以 HOLD_METHOD_CHANGE_REQUIRED 管理 |

所有超时检测、哈希核对和日志整理优先使用确定性脚本，不用模型轮询。不确定旧执行者是否结束时，先核实并完成受控 stop/wait/fence，再决定恢复；禁止并发重复 writer。超时不是授权杀死未知进程或执行生产变更。

## 告警之后必须追踪并处理

告警只是异常记录。每条异常必须绑定处理责任人、下一动作、处理期限和最后处理证据；不能发完告警就结束。
Work 在活跃执行回合内必须读取回执、定位入口或依赖失败，并完成已授权的修复和验证。需要服务器命令时，先制作可审核且符合现有门禁的合并执行步骤，提供准确命令与预期结果；不能把自身未提供命令说成 Owner 未授权。
若后台无法唤醒 Work，必须明确标记该入口 NOT_VERIFIED 或 UNAVAILABLE，并建立可验证的替代处理路径。禁止承诺“我一直监控”“等待就会完成”，除非真实后台机制已部署且有测试证据。
通知失败必须记录并重试有界的幂等投递；不能仅在聊天里声称 Owner 已收到。GitHub 有告警不等于这个聊天已被唤醒，更不等于 OpenClaw 已恢复开发。

## 不丢后续任务

任务状态、依赖、最后进度、错误、断点、回执及下一动作必须持久化。上下文切换、聊天结束、进程退出、重启和额度耗尽不能抹掉队列。
前置任务完成后，要验证制品和验收条件，再推进已授权的后继 READY 节点；不能停下来等 Owner 逐项催促。失败或 HOLD 要把受影响的下游依赖标为 BLOCKED，并继续不受影响的任务。
恢复前核对 canonical ledger、实际进程、唯一 epoch/fence、已发生副作用和 checkpoint；未查清的执行结果保持 UNKNOWN，不重复执行。断电恢复与备份恢复须经实测后才标记 PASS。
聊天结束不能充当持久执行者；没有后台执行证据时须明确任务已停止或待启动。

## 交付与验收

每项交付须绑定实际代码/制品、commit/tree/hash、测试与必要独立审查、安装回执及回滚证据。源码完成、CI PASS、已安装、实机验收通过必须分开。
不能以不断增加计划、监控草案或审查描述替代当前关键路径交付。P2 优先交付完整、可审核的一体安装与回滚包，然后实际安装验收；P3 用真实任务验证。
节点完成必须产生可读取终态；未完成须产生具体 blocker、保留断点和可执行下一动作。没有证据不能称 PASS；写入本规则不代表相关运行能力已实现。

### 后续项目按工种开发与三次 Owner 交付（2026年10月23日增补）

适用范围：Owner 已确认的后续其他项目。当前社区项目不拆分，窗口4唯一 Writer、既有 PM／UI 分工保持不变；本增补不恢复 P2 或官网72任务，不触发服务器操作、部署或权限变更。仅规定开发与交付标准，不代表能力已实现或项目已通过验收。

沿用 V2.7 第9.1、9.5、9.6、9.8节与第10章的原有开发链、角色权限、独立审计及 Release Gate；工种是项目职责划分，不新增一套常驻 Agent、任务账本或审批系统。项目小可兼岗，但责任、产出及验收责任须逐项明确；开发者不能兼任自己产物的独立测试或独立审计者。

| 工种 | 责任与必交产出 |
| --- | --- |
| 产品／PM | 明确目标用户、场景、范围与不做项、功能清单和可检验验收标准；负责流程原型与需求语义的唯一来源，管理需求版本及变更，组织 Owner 确认。 |
| 架构 | 核查资产复用、技术边界、数据模型、接口契约、权限与依赖、部署及回滚设计；明确技术风险和实施顺序。 |
| UI／交互 | 依据 PM 同版流程原型制作视觉／交互稿、视觉规范、交互状态及响应式要求，不独自定义或改变业务语义；覆盖加载、空态、失败、权限不足等必要状态。 |
| 前端 | 按已确认原型与接口实现界面和交互，交付代码、自测、构建与接口联调证据。 |
| 后端 | 按契约实现业务规则、数据与权限、接口和必要迁移，交付代码、自测及接口联调证据。 |
| 独立测试／QA | 开发前制定或核验独立验收用例；在冻结集成版本验证功能、端到端、异常与影响回归，独立记录缺陷及复测结论，不修改被测业务代码。 |
| 运维／发布 | 在既有权限内准备环境、部署包、配置引用、监控、备份恢复与回滚证据；执行获准的发布并记录实际运行版本，不把安装当验收。 |
| 根协调 | 维护同一父任务、依赖与 checkpoint，明确各工种负责人及唯一集成责任人；汇总证据、处理阻塞并向 Owner 交付整体验收包，不以逐个 helper 完工代替项目完成。 |

独立安全审计和程序 Release Gate 保留原有职责，不由上述兼岗规则合并或降级。前后端是否拆分按具体项目需要决定，不强制拆分。若拆分，开发前在同一任务契约中固定各自允许文件路径、接口版本（请求／响应／错误／权限／数据语义）、分支及基线 SHA、依赖顺序、合并方式和唯一集成责任人；公共文件由明确的单一 Writer 写入。不同职责不得在同一分支或相同文件上并发 push；交接先核对原 Writer 停止、未完成副作用、checkpoint 与执行权，再继续。不能仅因分了工种就增加生产写权限。

#### 三次 Owner 交付节点

Owner 接收的是同一项目的三个完整节点成果，不是每个 helper 的零散产物。每个节点均由根协调汇总、相应工种负责内容，并记录 Owner 对准确版本的明确确认；内部测试通过不等于 Owner 确认，沉默不算确认。三个 Owner 交付节点不替代适用的客户确认或安装部署验收环节。确认只覆盖对应设计、原型或验收范围，不替代支付、生产发布及其他需单独取得的授权。

1. 架构与功能设计
   - 交付：目标与范围／不做项、功能和业务流程、复用与新增边界、架构及数据／接口设计、工种与文件归属、风险依赖、实现顺序、独立测试验收标准。
   - 版本证据：设计文档路径及版本／commit／文件 hash、需求与接口版本、对应 task/spec，列出尚未核实的假设和阻塞。
   - 通过条件：范围、关键技术可行性、接口与验收标准可核验，阻断设计的问题已解除，Owner 明确确认这一版；关键能力未核实不得记 PASS。
   - 下一责任：PM 按确认范围制作流程原型并维护需求语义，UI／交互基于同版流程制作视觉／交互稿，架构维护接口与技术约束；受本节点阻塞的正式实现不得绕过确认先做。

2. 原型确认
   - 交付：可查看或操作的完整主流程原型、关键页面与交互／异常状态、响应式要求、与功能清单的对应关系及已知限制。
   - 版本证据：原型文件／可访问链接及固定版本或导出 hash、设计版本、必要截图或演示记录；明确哪些是静态展示、模拟数据或真实联通。
   - 通过条件：Owner 能核对核心流程及界面，关键交互和范围分歧已解决，并明确确认这一版；原型可点击不代表后端、真实付款或生产能力已完成。
   - 下一责任：前后端按确认原型与契约实施，唯一集成责任人汇总同一候选版本，QA 独立验证，运维准备获准范围内的交付条件。

3. 整体验收
   - 交付：覆盖确认范围的单一集成候选、功能对照清单、独立 QA 报告、适用安全审计与门禁证据、操作说明、已知限制，以及适用部署／回滚包与回执。
   - 版本证据：目标仓库与分支、完整 commit/tree、构建与 artifact hash、依赖锁、用例集版本、环境／配置版本、CI run 与独测结果、缺陷及复测证据、准确验收入口；所有证据必须对应同一集成候选。
   - 通过条件：确认范围内端到端功能及所有适用门禁通过，无未关闭的阻断性缺陷；非阻断遗留项明确影响、责任人、期限并取得 Owner 接受，且 Owner 确认该版本的整体验收结论。失败、缺证、UNKNOWN、NOT_TESTED 均不得填 PASS。
   - 下一责任：根协调记录验收结论和交付移交；运维仅按已有有效授权进入发布或维护。若本次验收只覆盖离线／模拟／测试环境，结论必须限定该范围；生产部署、实机验收及真实业务链路另列状态，不得据此宣称生产可用。

#### 共用证据、缺陷与阻塞闭环

每次提交 Owner 的交付记录沿用原 task/spec/checkpoint，至少包含：节点、内容清单、准确版本、证据链接、实际验证环境、通过／未通过项、Owner 确认记录、缺陷／阻塞、下一责任人、下一动作与期限。证据引用不可只写易变分支名、“最新版本”或口头完成；没有代码的设计与原型可用固定文档／制品版本及 hash，不伪造代码 SHA。

缺陷记录须包含复现步骤、预期／实际、环境与版本、影响级别、修复责任人和期限。开发修复后形成新版本，由独立 QA 复测失败用例及影响回归；相关旧测试、审计和确认不得冒用于修改后的候选，按影响更新证据并重新确认受影响节点。代码自测和 CI 不能替代独测，独测不能替代独立安全审计。

受阻节点按既有 FAIL／HOLD／BLOCKED 机制保存证据与断点，明确缺失依赖、解除责任人、下一检查时点；继续不受影响且已授权的工作，不以跳过确认、并发重复 Writer 或伪造证据解除阻塞。需求、原型、接口或验收范围变更回到受影响节点确认，不能悄悄扩项。

整体交付必须来自已集成并验证的统一版本；helper 的局部完成、自测或文件集合只作为输入，不逐个交给 Owner 充当整体验收。生产、STAGING／CANARY、离线与模拟结果分别记录，模拟测试通过不冒充生产或真实交易通过；本增补不新增部署、采购、凭据或持久访问授权。

## Dots 原生开发的模型例外与额度边界

Owner 在2026年10月12日明确：禁止 Astra 的原意是避免高额消耗 Work／Codex 额度。Work／Codex 额度不足时，允许 Dots 使用自身原生模型直接生成和修改代码，作为同一闭环的开发执行入口；该用途不再因 Dots 原生 Astra 模型而被禁止。此例外仅适用于 Dots 原生执行，不修改英国 Worker 的既有模型政策，不允许付费 API，也不允许 Dots 暗中转交 Work、Codex CLI、app-server 或其他 Codex 推理执行者。

三个入口为 Dots、普通 ChatGPT 聊天及 Work，共享现有任务、spec、canonical ledger、断点和验收门禁。切换前必须对账并完成原 writer 的停止／执行权移交，每次只有一个有效 writer，不重建任务、不重置预算。英国侧优先以确定性脚本执行测试、哈希核验、部署步骤和回传。Dots 的原生深度工作额度、普通聊天额度和 Work／Codex 额度分别记录；UNKNOWN 保持 UNKNOWN。原生模型名称不能证明额度归属；没有 Work／Codex 剩余额度也不能证明 Dots 不会调用它们。Dots 深度工作不是已证明无限额度，只有实际调用路径和额度证据才能认定成功节省了 Work／Codex 用量。

能力验收须覆盖 Dots 直接写代码并提交 GitHub、英国脚本执行、终态回传和继续下一任务，以及禁止 Work／Codex 推理的测试条件。书面策略生效不等于该接力能力已经部署。
