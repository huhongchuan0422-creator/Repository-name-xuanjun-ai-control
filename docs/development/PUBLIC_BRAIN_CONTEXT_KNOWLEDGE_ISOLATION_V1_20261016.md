# 玄钧公共大脑：平台、项目、商家、门店、个人五层知识隔离 V1

2026-10-16 Owner规则；SOURCE_ONLY / PRODUCTION_HOLD。优先复用现有公共大脑、CRM、Identity/Project、已有社区三渠道身份关联及知识资产，不建立第二套平台CRM。关联 PLATFORM_VS_PROJECT_END_USER_ISOLATION_20261016.md、UNIFIED_CRM_CHANNEL_REFERRAL_REUSE_20261016.md。

## 一、上下文不是固定用户等级
每条消息在可信服务端决定 business_domain, tenant_id, project_id, current_role, merchant_id, store_id, project_user_id, platform_customer_id, session_id, authorized_resources 和知识/事实版本。扫码入口只是商家上下文线索，不是查看订单的授权。不得让LLM或客户端自行提升scope。
L1 玄钧平台：定制开发、SaaS、生态、平台订单及CRM，只能访问玄钧平台核准的公共/客户授权资料。
L2 项目公共知识：社区分账等单项目规则、公开入驻与帮助。
L3 商户经营及入驻：公开入驻咨询可匿名，实际商家管理、认证材料、后台须经商户身份和项目授权。
L4 特定商家/门店消费：来源于A的扫码/店铺页面，只读取A及对应门店有效菜单、商品、营业信息，并允许项目已批准通用帮助；不得读取商家B的业务事实。
L5 消费者本人事务：订单、优惠、退款及售后必须再核对项目终端用户身份及订单归属，商家二维码、订单号或自报手机号不构成认证。

## 二、数据隔离与可信事实
公共大脑复用模型推理和路由，但知识源在查询前后都经过 project+merchant+store+visibility+ACL 服务端过滤；提示词不能代替数据库级权限。不同商家私有文档、价格、客户资料不得跨域进入向量搜索结果、工具上下文、缓存或对话摘要。
价格、库存、订单、支付、退款等实时事实仅从对应商家/门店受控业务API读取，不由通用RAG、过期索引或模型推测。例：A煎饼7元、B煎饼8元，问A只回答A实时价格7元；A数据接口不可用就说明无法确认A的当前售价，不借用B的8元。
用户从A进入B，必须在服务端重新绑定active_context，清除或隔离A的检索结果、临时权限、工具与缓存；会话历史不得在B的上下文中泄露A的私有信息。

## 三、三渠道和两类身份
玄钧平台Telegram、用户飞书、网站AI绑定同一平台customer_id；定制项目终端用户使用独立(project_id,project_user_id)，不因咨询项目AI自动成为玄钧平台Customer。渠道事件绑定对应场景、租户、项目、商户、门店、会话及经验证角色。开发飞书、币安飞书、用户飞书凭据与通知权限完全隔离。
同一人可同时咨询玄钧平台、社区公共政策、商户A、自己的订单，但每次必须明确上下文。模糊时询问商家/门店或只答允许的项目公共知识；跨域请求分解且逐项验权。玄钧推荐关系与项目自己的用户推荐必须隔离。

## 四、知识维护和追溯
玄钧平台知识由玄钧授权管理员发布；项目规则由对应项目运营方批准；商家菜单由商家有权人员维护，真实价格由交易系统权威数据提供。知识草案→独立审核→批准→生效→撤回/替代，记录版本、作者、Owner、时间、来源、哈希与访问scope。客户上传或聊天内容不能自动进入公共知识或模型训练。
每次回答留业务上下文、所用知识版本、事实API来源、模型版本与权限决策的最少必要审计；缓存必须按完整scope隔离，撤销后立即失效或阻止读取。

## 五、集中验收
1. 商家A价格7、B价格8，在A只能得到7；A事实缺失必须拒绝推断B价格。
2. 同一用户由商家A切换B，不继承A私有消息、资料、缓存或授权。
3. 匿名可查公开入驻规则，不能查商户审批与私人订单。
4. 商户A管理员不能查看商户B或其他项目数据。
5. 查询本人订单必须验项目用户/订单归属；不存在时不泄漏其他客户订单。
6. 玄钧平台、社区项目及商家层知识隔离，不能因为共用CRM或公共模型而交叉污染。
7. 三渠道跨端和重新绑定测试、撤权、重放、缓存过期、知识撤回、事实API超时、UNKNOWN等负向路径。
8. 必须验证服务端检索/数据库层强制权限，禁止仅用提示词隔离；全部实际测试绑定精确CI及独立审核。
